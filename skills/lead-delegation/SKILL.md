# 主导委派

主 Agent 对用户目标和最终交付负责。子 Agent 对分配到的任务负责，并提供可核验的产物与证据。

## 1. 确定目标与任务依赖

- 从用户请求提取可观察的验收标准，查明影响拆分的事实，例如共享接口、现有改动和适用的项目规则。把尚待核实的判断写成调研任务。
- 只有会改变交付目标、兼容承诺或必须获得新授权的决定才交给用户。说明每个可行选项能达到什么结果，以及成本和风险。
- 有依赖的任务等到前置产物可用再启动。独立调研、独立审查和写入范围互斥的实现可并行。例：接口改动与现有测试缺口审计可并行，依赖新接口的页面实现在接口契约可用后开始。
- 委派以用户的请求和当前宿主规则为准。用户要求委派单个小任务时，使用短任务说明。用户把执行方式交给你时，按委派和验收的开销判断是否直接完成。

## 2. 写任务并准备工作区

- 每项任务写清目标、交付物、可写范围和验收方式。跨文件、需要隔离或涉及多个依赖的任务，使用[任务模板](references/task-template.md)。
- 只读子任务明确交付证据及来源。并行写入同一工作区时划定互斥的写入范围，并检查共享生成物、锁文件、端口或测试数据是否会冲突。可能冲突的任务用独立工作区，或按顺序执行。
- 确认子 Agent 能读到任务依赖的版本。隔离工作区通常从已记录的版本开始，依赖未提交改动时，优先采用宿主支持且能保留现有改动的交接方式。也可把依赖任务安排到原工作区依次执行。把用户已有改动纳入提交前，确认这些改动也在授权范围内。
- 带上任务相关的项目约束和已获授权。提交、推送、发消息及其他外部操作分别服从实际授权。

## 3. 派发并跟进

- 使用当前宿主提供的委派工具及其文档，遵守指定的 Agent、模型、隔离方式和并发限制。所需能力不可用时，报告具体缺口，继续推进可独立完成的工作。委派权限和工具状态以宿主为准。
- 派发超时且结果不明确时，先通过宿主支持的任务状态或请求标识确认是否已创建。支持幂等重试时沿用原请求标识。宿主无法确认或取消时，将该任务及其下游标记为阻塞，继续独立工作。汇报时写明恢复条件，等到能确认原任务不存在或已停止再重新派发同一写入范围。
- 多项任务或需要跨轮次跟进时，维护简短台账。记录用户目标、相关授权，以及各工作项的依赖、负责人、任务链接或标识、工作区或基线、状态、产物和下一步。按派发、返工、验收和集成事件更新。
- 用宿主支持的等待或通知机制跟进。子 Agent 回报完成后，查看任务结果与产物。方向有变化时，使用宿主支持的更正或取消操作，并更新受影响的下游任务。

## 4. 验收并集成

- 对照用户目标和[验收清单](references/review-checklist.md)检查实际产物。需要返工时，提供具体位置、用户影响和验收标准，按宿主的规则跟进。
- 按依赖顺序集成已验收的产物。检查合并后的版本和关键调用链，对组合行为或解决冲突后受影响的路径补做验证。提交、推送或合并仅在任务要求与授权范围内执行。
- 汇报用户目标是否达成、产物位置、已执行的验证和仍待处理的事项。子 Agent 的验证结果与主 Agent 亲自执行的结果分别注明来源。台账中的完成状态以用户要求的交付节点为准。
