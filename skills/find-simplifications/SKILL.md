# 寻找简化候选

把“帮我找可以简化的地方”变成**有证据的候选清单**：少而扎实，胜过一堆“看起来复杂”的猜测。默认只读，不修改代码；用户要求实施时再单独计划。

## 先读上下文

优先阅读仓库的工程规范与架构文档（如 `AGENTS.md`、`CLAUDE.md`、`CONTRIBUTING.md` 以及待审计模块对应的设计文档）。先弄清哪些设计是**有意保留**的，再作判断。

### 默认保护，不当作简化目标

已发布或持续演进的项目中，以下内容通常承担兼容或语义约束；除非用户明确要求或有强证据，不提议删除或合并：

- 面向特定上游版本、运行环境或平台的兼容适配、降级分支与能力探测；
- 为保留不同外部系统、插件或适配器原生语义而刻意分开的实现，不因“长得像”而硬抽成统一抽象；
- 对外公共契约（SDK、插件接口、CLI 参数、HTTP/RPC 协议）、配置文件与持久化存储格式及其向后兼容读取路径；
- 代理或路由链路中的原样转发路径、安全与权限边界；
- 明确标为历史归档、事故复盘或兼容基线的目录与文档。

## 强候选

- 公共方法、事件、配置项、导出或辅助函数**没有生产调用方**，只被测试或文档引用，且所钉住的行为并非承重契约。
- 同一事实存在两份互相镜像的数据表示或状态同步层。
- 接口里每个实现都被迫提供、却没有任何消费者使用的方法。
- 为没有明确需求或负责人的“以后可能需要”设计的通用性：未使用的选项、注册表、插件点、空扩展钩子。
- 只为保护一个未被使用的 API 而存在的校验、回滚路径或特例测试。
- 对同进程、已有静态类型或所有权保障的调用做的多余防御性拷贝、冻结或重复校验，且来源说明不了其必要理由。
- 手写实现了现有依赖或运行时下限已内置的能力，替换后可连同其专用测试一并删除。
- 行为略有差异，但简化后的行为更一致、更易解释且不破坏对外契约。

**不是候选**：只修一个笔误、未经调用方证明的“这里看起来复杂”、以及被文档或兼容约束明确保护的设计。

## 证明或驳回

先按当前仓库的实际布局划分语料，再对每个符号或行为分类调用方：

- **生产语料**：核心源码目录、应用入口、构建/发布脚本、运行时装载与配置路径。
- **非生产语料**：测试、文档、快照、fixtures、示例代码、注释。
- **模糊语料**：`tools/`、`scripts/`、运维/诊断/冒烟探测脚本，可能是发布或验证承重路径，先读真实用法再归类。

用 `rg` 搜精确符号、事件名、配置键、方法调用形式（如 `.name(` 与 `name(`）、线协议或路由字符串，并实读调用点。LSP 或类型检查工具可辅助，不能替代对动态引用、反射、配置装载、测试和文档路径的理解。

**驳回或降级条件**：
- 存在真实生产调用方（那是产品或功能决策，而非简化清理）；
- 被已记录的设计或防御性理由保护，且新证据不足以推翻；
- 会引发大面积无关改动却没有真正缩小公共 API 或理解成本；
- 方向正确但收益很小（建议留一条带上下文的 `TODO(tag)` 即可）。

**删改前再核对四件事**：
1. 是否触及持久化数据、迁移或配置格式兼容；
2. 是否属于对外契约（插件、SDK、CLI、协议）；
3. 是否有上游或历史版本兼容原因；
4. 是否有跨平台或不同运行环境的差异原因。

## 输出

对每个候选给出：

1. **对象与位置**（文件、符号）。
2. **调用方证据**：生产与非生产分开列，附搜索方式。
3. **建议动作**：删除、合并、降级或改用依赖，以及需要同步清理的测试、文档与导出。
4. **放弃什么**：最强的反对理由。
5. **风险与兼容性**：持久化、公共契约、版本与跨平台兼容。

最后列出被排除的“看似可简化”项及排除原因。是否落成重构计划或提案文档由用户决定，不自动新建文档体系或修改代码。
